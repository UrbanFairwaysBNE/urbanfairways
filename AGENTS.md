# Project rules
- Customer review visibility uses the membership-verification predicate so completed approvals disappear immediately without deleting the stored decision.
- Complimentary assignment uses an authenticated admin-only function and existing custom billing; reject existing subscriptions/checkouts rather than silently retaining charges, block self-service checkout for custom billing, and protect profile tier/billing writes from non-admins.
- Bay shutdown uses one serialized, bounded operation with live booking rechecks; simulator executables are tree-killed separately from window-title detection. Independent visible-window and named-process verification of the simulator executables only (other leftover apps never fail a shutdown or block a changeover) determines closure, not kill-command exit codes; failed/missing verification stays unknown, and Health Check separates unknown shutdowns from confirmed remaining processes.
- Execute shutdown PowerShell scripts via execFile and UTF-16LE EncodedCommand, never a cmd.exe command string, so quoted pipes cannot break close verification.
- Bay Controller requires Electron 39.8.7+ (28.x crashes with 0xc000041d during display hot-plug); crashReporter captures native crashes locally and self-reports controller_crash_detected on next launch, which Health Check counts as red.
- Simulator lifecycle evidence lives in a bounded acknowledged main-process disk journal, drains through existing log ingestion, identifies instances by PID plus creation time, and uses a shared launch/shutdown gate; lookup failures remain unknown so reloads cannot silently duplicate or falsely close apps.
- Renderer shutdown callers coalesce onto one verified request; different-customer back-to-back changeovers exclusively own settings restoration and launch, blocking ordinary automation so outgoing settings cannot race incoming settings.
- GSPro settings are written once per booking through the shared serialized session-settings preparer (power-on window for standalone bookings, after verified close in changeovers, launch only as a fallback) and Electron refuses settings writes unless GSPro is confirmed closed, swapping files in atomically, because GSPro reads them while starting.
- Lesson tiles resolve the linked customer separately from the paying booker; both range ingestion endpoints resolve the owner from the stored booking and use that owner for session rows and CSV paths, so coach billing/settings remain unchanged and lesson data never falls back to the coach.
- Marketing and bulk email senders must recheck profile opt-out and recorded unsubscribes at send time, and use recipient-specific signed public unsubscribe links in the shared footer; the same endpoint supports authenticated admin opt-out and keeps legacy email links valid so existing recipients are not stranded.
- Generate public/sitemap.xml through scripts/generate-sitemap.ts before dev/build; keep its paths aligned with public indexable routes, exclude app/auth/admin/redirects, and omit lastmod without authoritative page-specific timestamps so crawlers discover only intended website content.
- Store booking durations as numeric hours, not integers, so the existing half-hour booking flow preserves fractional durations through confirmation.
- Lesson confirmation/reschedule emails and SMS use the shared lesson-door-access helper after template rendering for both recipients, so edited templates cannot accidentally omit the resolved booking-day code; disabled sends and cancellations remain unchanged.
- Retired public marketing pages redirect to a relevant active page while preserving their source for later restoration; hiding a promotion must not delete its admin tools or competition history.
- Keep system-switchover notices separate from promotional campaign composition; the dedicated admin tab is preparation-only so reviewing a notice cannot trigger billing changes or customer sends.
- Create and edit timetable blocks through the same AddBookingDialog form and shared block duration validation, to keep availability checks and limits consistent.
- Keep the retired first-session promotion endpoint a no-op and its database award guards in place; this prevents both direct invocations and old in-flight batches from crediting imported customers.
- Any future first-session eligibility query must exclude profiles with first_session_promo_exempt=true; the explicit flag preserves exclusions independently of sent-email history or whether the promotion is enabled.- Door codes: TTLock pushes each code to every venue lock (lock IDs in door_access_settings.tuya_device_id, comma-separated) and stores "lockId:pwdId,..." in provider_ref, so one revoke removes it from all doors.
- Tiers flagged requires_verification (frontline) set profiles.verification_status='pending' at signup via notify-frontline-signup; admins approve or decline from the customer profile dialog in AdminCustomers, and declining never cancels the membership automatically.
- Settings → Health Check reads bay controller activity from the trigger-maintained bay_health_daily rollup (via platform_health RPC), never by scanning bay_controller_logs live, because that table grows by ~300k rows/day and live scans time out.
- Shutdown warning recovery is reconciled in a compact event table by bay, booking and local event time; subtract only matched ambiguous warnings, preserve confirmed-running failures, and label legacy message-only closure as reported rather than independently verified.
- door-code-manager accepts full actions only from the service-role key or admin JWTs; unauthenticated calls may only run daily_ensure/sync and receive a bare success flag, and lock key material is stripped from diagnostics, because door codes and remote unlock must never be publicly reachable.
